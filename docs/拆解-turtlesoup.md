# 海龟汤拆解（2026-11-24）

只看公开资料：维基百科「Situation puzzle」、人人都是产品经理和少数派上 AI 海龟汤的开发文章、LatEval（LREC-COLING 2024）、TurtleBench（arXiv 2410.05262）、TurtleSoup-Bench（arXiv 2508.10358）。没有照抄任何谜题原文，本项目 24 道题全部原创。

## 1. 规则本体

- 名字：英文叫 situation puzzle / lateral thinking puzzle（水平思考谜题），日本叫「ウミガメのスープ」，中文圈叫海龟汤。
- 角色：**汤主**（主持人，知道真相）+ **猜题者**（一个或多个）。
- 汤面：一段离奇但完整的故事片段，公开给所有人。
- 汤底：完整的真相，只有汤主知道。
- 猜题者只能问「能用是 / 否回答」的问题。汤主的回答通行四种：
  - **是**、**不是**；
  - **无关**（和真相无关，或者答案不影响推理）；
  - **是也不是**（英文圈叫 yope：问题里一半对一半错，直接答是或不是都会误导）。
  - 少数玩法还有「无关，但可以当作是」之类的变体，主流产品不用。
- 胜利条件：说出汤主心中的那个故事，**包括汤面里那个反常点的解释**。很多解释都说得通，但目标是汤主的版本。
- 难一点的玩法会限制提问次数。

## 2. 谜题分类（中文社区和产品里的叫法）

| 维度 | 叫法 | 含义 |
|---|---|---|
| 有没有人死 | 红汤 / 清汤 | 红汤有死亡情节；清汤没有 |
| 有没有超自然 | 本格 / 变格 | 本格是现实逻辑；变格允许灵异、科幻、超能力 |
| 风格 | 黑汤等 | 部分社区把阴暗重口的单列，各家定义不统一 |
| 难度 | 简单 / 中等 / 困难 | 小程序和 App 常按难度分档挑题 |

TurtleSoup-Bench 按题材分了犯罪、心理、超自然、反转、巧思五类，模型在「巧思」和「心理」两类上分数最低。

## 3. 线下和线上的主流做法

- **线下（剧本杀店、桌游店、聚会）**：一个人当汤主，几个人自由抢问，问答全部公开，常常不限次数，有人能讲清整个故事就算破汤，汤主揭晓汤底。节奏靠汤主控场，偏得太远时汤主会给提示。
- **小程序 / App 的 AI 汤主**（人人都是产品经理一文的流程）：选汤底类型 → 给出汤面并告诉你有几次提问机会 → 每答一次提示剩余次数，**最后一次提问时提醒可以还原** → 玩家申请还原，AI 按「一致性和完整程度」打分（满分 10 分）→ 公布评分和汤底。超过次数还在提问就判失败。
- **多人 AI 海龟汤**（少数派「出前一汤」）：多人即时推理，额外加了搜证、角色对话、线索白板等玩法。架构上把「思考」和「表达」分开：题目入库时用强模型离线拆好逻辑档案（诡计、物证、角色盲区），实时对话交给快模型照档案回答。作者踩过的坑：只靠一段塞了汤底的提示词，要么慢、要么逻辑松；用语义相似度缓存回答会把「自杀」和「被杀」当成同一个问题。
- **开源**：有把 LLM 变成汤主的 MCP 服务（回答限定 是 / 不是 / 无关 / 是也不是，拿到关键线索时提醒玩家总结）；有只让模型在预设候选答案里挑的汤主，目的是降低泄底风险。

## 4. 成熟方案怎样判定「还原成功」

- **要点覆盖**是公认做法：
  - LatEval：每道题标注若干「关键线索」，汤主模型数玩家最终推断覆盖了几条，得分叫 Answer Consistency。另外三个指标：提问和关键线索的相关度、问题之间的发散度、平均提问轮数（太少说明没收集信息，太多说明卡住了）。
  - TurtleSoup-Bench：判定模型从汤底抽出 2–5 条核心逻辑点和 3–8 条细节点，和玩家的总结做语义匹配（≥0.5 算命中），总分 = 0.3 × 逻辑 + 0.3 × 细节 + 0.4 × 结论。
  - 小程序：按完整程度打 10 分制。
- **判定本身会出错**：TurtleBench 收集了上线两周 4000 多名用户的 2.6 万次猜测，用户最大的抱怨是「AI 判定不合理」。常见毛病：盯着一个词就判对、同一个猜测前后判得不一样、判错时废话特别多；「不对」和「无法判断」人都很难分清。所以要点要写得**具体、可核对**，判定只问「每条要点说到没有」，不让判定者自由打分。
- 汤主答题的准确率：LatEval 里 GPT-4 当汤主人工核对 90% 以上答对，弱一些的模型 80% 左右——汤主会答错，但大体可靠。

## 5. 提示和节奏

- 提问次数有上限、实时显示剩余次数，最后几问提醒还原（小程序做法）。
- 分层提示（先暗示范围再缩小方向）多见于单人 App；多人对战里提示会破坏公平，一般不给。
- LLM 当猜题者的典型失败（TurtleSoup-Bench）：死抠字面意思、不会把线索拼成完整场景、想不到反常动机、被答了「不是」还在原方向上打转。提示词里要提醒「先问大范围、别纠缠被否定的方向」。

## 6. 观战看点

- 每一问落地、汤主盖下「是 / 不是」的那一刻——问到点子上的问题最有戏。
- 还原失败时公开「命中几条」：观众和对手都能看出谁离真相最近。
- 终局揭晓汤底，对照要点看每个人卡在哪一环。
- 大模型对比：谁的问题更会划范围、谁被「不是」之后会换方向、谁急着还原。

## 7. 我们的做法：采用、简化和理由

**采用**
- 汤主 + 猜题者，汤面公开、汤底隐藏；回答只有 是 / 不是 / 无关 / 是也不是 四种，可加一句 ≤20 字的补充（线下汤主常做的澄清，比如「问的人不对」）。
- 要点覆盖判定还原：每题 3–5 个要点，汤主逐条判定命中哪几条，命中全部才算成功（和 LatEval 的关键线索、成熟产品的完整度一致）。
- 提问上限、剩余次数随时可见，用完后再给每人一次还原机会（小程序「最后一问提醒还原」的多人版）。
- 红汤 / 清汤、本格 / 变格、三档难度都有。

**改动和简化**
- **轮流行动，不抢答**：线下是自由抢问；对战平台按座位轮流，每回合二选一「提问」或「还原」，保证每个模型机会均等、观众看得清。
- **还原次数上限 2 次**：防止靠反复还原试错。还原的命中情况（几条、哪几条，不给要点原文）公开，失败也会把线索送给对手，这是要权衡的风险。
- **全场提问共用 猜题人数 × 8 次**：LatEval 单人上限 20 问、TurtleSoup-Bench 30 问；多人共享问答信息，人均 8 问够用又不会拖太久（4 人局 24 问，一问一答连停顿约 10 秒，一盘 5–8 分钟）。
- **超时放弃本回合也占一个提问名额**：不扣还原次数，但保证全员挂机时对局也能结束。
- **名次**：还原成功的第一；其余按最好一次还原命中的要点数排，并列同名次；没人成功且命中数都一样就是平局。汤主只主持、不计积分（`outcome.unrated`），名次和最后一名相同。
- **汤主没有输赢**，提示词里写明必须如实回答、不能剧透、不能被猜题者的话带偏（防提示注入）。
- **内置汤主不用大模型**：问题和要点关键词粗略匹配（答不上就「无关」），判定按要点关键词。这比 LLM 汤主粗糙得多，但能让没有 API 的对局跑完；真正比赛用模型或真人当汤主。
  - 性别不当普通关键词：只有问主角（「主角 / 主人公 / 主角的称呼 / 他、她」+「是男的 / 女的吗」）才按题目的 `hero` 答，问配角的性别一律「无关」。早先把「女人」放进词表，「照片里的女人认识他吗」「凶手是男的吗」都会答反。
  - 「还有别人吗」只在别的词都没对上时按题目的 `others`（默认有）答，不会压过「是别人在开玩笑吗」里的「玩笑」。
- **不做**：分层提示、搜证、角色对话、10 分制打分（命中几条要点已经够用，且更好核对）。

**谜题库**：24 道原创题，三档难度各 8 道；红汤 11、清汤 13；变格 4 道（灵异、时间循环）。死亡情节点到为止，不写血腥细节。每道题带标题、汤面（≤120 字）、汤底（≤300 字）、3–5 个要点（一句话 + 关键词）、内置汤主用的真假词表、主角性别和称呼、内置猜题者会问的问题（前几条对应要点、答「是」，后几条是错误方向、答「不是」，测试逐条核对）。`setup.puzzle` 指定编号，默认按种子挑。要点只收「解释汤面反常点必需的环节」：《一口没吃》原来的第 3 点「那桌菜给员工吃了」是汤面推不出也不影响解释的细节，换成了「新菜单让生意变好，所以老板道谢」；《阳台的花盆》是红汤，汤底补上「当场身亡」。

**画面**（`web/stage/turtlesoup.js`，对称座位版式的中间舞台）
- 汤面卡常驻：用纸面卡而不是 `.panel`，对局页放不下时折叠面板也不会把它收成按钮；手机上也一直在页面里。
- 汤底：汤主（进行中）和终局常驻展开（框内滚动）；上帝视角的观众默认收着，点汤面卡右上角「看汤底」展开；不剧透视角和猜题者的视角里根本没有汤底数据。
- 问答流：标题行带剩余提问和每人「还原次数 + 最好命中」；列表限高、自动跟到最新一条，往上翻过就不跟；收成按钮后弹出的卡片里最新的在最上面。
- 真人猜题者：一个输入框（回车提问，还原要点按钮，免得误用掉还原机会），标题行写第几问、全场还剩几问、还能还原几次；真人汤主：要回应的原话在最上面，四枚印章 + 一句补充；判定时勾选命中的要点。
